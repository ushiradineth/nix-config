# Ideas, briefs and new UI

## Find the visual authority

Decide whether the task preserves an existing identity, expands it to a new surface, or replaces it.
Use rendered pages, real assets, reusable components and current brand guidance as evidence. A
missing DESIGN.md is not permission to invent a new brand. A redesign preserves product truth,
essential behavior, native affordances and scope while deliberately replacing the requested look.

Frame the task around the audience, primary action, real content and the surface's mode. Reuse
settled context; ask for a consequential missing product choice rather than CSS preferences.

## Brainstorm or shape

For UI brainstorming, explore materially different ways to organize the user's task. Give each
concept a spatial or interaction thesis: what leads, what groups, what stays visible and what the
user does next. Explain the advantage, tradeoff and fit to this product. Changing only color and
border radius is one concept in several costumes.

Two or three strong options are usually more useful than a long style catalog. For a well-specified
brief, develop its direction instead of manufacturing a choice. Useful comparison axes include:

- a task-first workspace versus an overview leading into focused work;
- a compact expert surface versus progressive disclosure for occasional use;
- an editorial story versus a demonstrative product-led composition;
- how actual imagery, type, data or interaction supplies the focal point.

`shape` returns the smallest actionable brief: job, outcome, selected or recommended direction,
scope, important states/content ranges, responsive intent and real open decisions. Brainstorming and
planning stop before implementation unless the user requested it too. Do not create a plan file or
demand a confirmation round merely to restate settled decisions.

## Build or redesign

When implementation is requested, carry the strongest supported direction into code in this session.
Ask for a selection when genuinely incompatible product/art directions remain open; keep working on
source and constraint discovery while awaiting that choice.

- **Operate:** make navigation, selection, editing and save behavior consistent. Use the existing
  component library and semantic states. Dense data can be appropriate; novelty must earn its cost.
- **Read:** establish a clear reading path, comfortable measure, useful navigation and quiet
  metadata. Avoid treating documentation as a conversion funnel.
- **Persuade:** let real product evidence, a meaningful image or a distinctive typographic idea
  organize the composition. Connect the promise to a clear action. Never invent testimonials,
  customer counts, capabilities, pricing or product screenshots.
- **Experience:** give the work space and a direct route into it. Navigation and decoration should
  not compete with the artifact.

Translate the direction into a coherent system: composition, type roles, color relationships,
spacing rhythm, imagery, components and interaction. Honor pinned aesthetics even when they differ
from generic anti-pattern advice. Fit ambition to the mode: an operational dashboard does not need a
marketing-page hero, display type or theatrical load sequence.

Build the complete scoped path with real content, responsive structure and relevant loading, empty,
error and success states. Use the project's assets and toolchain. Add assets, dependencies or
services only within its actual task authority. Inspect the render and behavior before calling the
direction successful; use [finish](finish.md) after structural work is settled.

## Variants and previews

`generate` or an alternatives request compares distinct compositions or interaction choices on one
named target. Use the requested count, or a small useful set. Preserve unrelated source. Isolate
competing implementations, or use disposable previews, so evaluating one does not erase another.

Use the available screenshot, prototype or image tools when they clarify the choice. Label concept
images as concepts; they do not prove implementation. Show the relevant differences and tradeoffs.
Brainstorming stops with options. When the user requested a build and delegated the choice, select
and implement; when they asked to choose themselves, wait for that selection before discarding or
integrating alternatives. Do not install a live-picker service to produce ordinary previews.
